# TRIMP 全天心肺负荷与循序提升基线设计

**状态：** 已确认产品方向；待文档审阅，尚未实施

**日期：** 2026-09-04
**取代范围：** 新版本取代首页使用的 `whoop-style-v2` 全天 Strain（0–21）。v3 不迁移、不 in-place 改写既有 v2 行，二者始终可按版本追溯；既有 v2 管线仍可在其自身输入修订时按原规则回补重算。现有 v2 Recovery 是 v3 可用负荷的版本化动态输入，详见 §6.2 与 §7。

## 1. 决策与边界

产品的核心目标不是复刻 WHOOP 的私有 0–21 分数，而是提供一个能在当天持续累积、可复算、可解释的 **全天心肺负荷**，并以个人历史和早晨恢复状态给出当日可用负荷与会随持续完成量跟随的本周提升基线。

首页同时呈现三个不混淆的量：

| 名称 | 含义 | 恢复状态是否改变数值 |
| --- | --- | --- |
| 全天心肺负荷 | 已发生的、由有效心率与活动证据计算的 TRIMP | 否；历史事实不事后扣分 |
| 今日可用负荷 | 今天在当前恢复状态下的个人参考上沿 | 是；恢复差时可用空间更小 |
| 本周提升基线 | 以历史周负荷自动跟随的训练方向 | 不因单日波动重算；每周更新 |

例如，已经获得 `42 TRIMP` 的用户，恢复好时可能有 `65 TRIMP` 的今日可用负荷（使用率 65%）；恢复差时可能是 `45 TRIMP`（使用率 93%）。两种情况下，实际负荷始终是 42。

这不是医疗诊断、受伤预测或“可以/不可以训练”的许可。超过参考上沿只触发“后续降低强度、不要为了追基线强行加练”的建议；胸痛、明显不适、疾病或临床风险须以医疗专业意见为准。

## 2. 研究与公开算法依据

1. Google Health 的公开帮助文档说明，其 Cardio Load 基于 TRIMP，使用年龄、静息心率和性别；周目标比较最近一周与最近一个月（ACWR），并考虑维持或提高体能的目标和恢复状态。它要求至少 7 天校准，28 天连续佩戴可得到更可靠结果。
   - https://support.google.com/googlehealth/answer/15402655
2. Google 的公开技术白皮书进一步给出分钟级的 Banister TRIMP 公式、30% 心率储备阈值、活动/动作证据要求，以及周目标的 `max(RM, EWMA)` 结构。该文是 Google 的技术白皮书，不应表述为独立临床验证或其私有产品的逐位复刻。
   - https://arxiv.org/abs/2508.11613
3. 7/28 天 EWMA 与 ACWR 是训练负荷研究中常见的时间尺度；`λ = 2/(N+1)` 是公开的 EWMA 取法。
   - https://pmc.ncbi.nlm.nih.gov/articles/PMC6041726/
4. ACWR 只能描述近期负荷相对历史的变化，不能被显示为个人受伤概率或通用安全阈值。有关其偏差、稀疏数据与因果局限已有系统性批评。
   - https://pubmed.ncbi.nlm.nih.gov/32125672/
5. HRV/恢复状态可用于调整训练安排，但系统综述没有给出可推广到所有消费者的“恢复 60 分 = 允许负荷乘以某个常数”的公式。因此本设计不用固定恢复乘数。
   - https://pmc.ncbi.nlm.nih.gov/articles/PMC8507742/

## 3. 数据可得性与与 Google 的差异

Google 的设备端 Cardio Load 使用惯性传感器确认升高心率来自身体活动而非心理压力，并对 30%–40% HRR 的低端区间使用额外下调；公开材料没有给出该下调的可复刻函数。当前 Google Health API 已同步到本项目的数据没有原始惯性传感器流；本账户的 raw `heart-rate` 点也没有 `motionContext`。因此本项目实现的是 **Banister HRR-TRIMP 的 API 可实现变体**：采用公开的 30% 阈值与 HRR 非线性项，但不采用 Google 未公开的 30%–40% 下调，也不能承诺与 Google App 的绝对数值一致。

可用输入与替代规则：

| 需求 | 可用输入 | 用法 |
| --- | --- | --- |
| 分钟心率 | `heart-rate` 分钟聚合 | 使用本地聚合、由最多 75 秒 sample hold 推导出的有效覆盖；每分钟保存最小化的、带 BPM 的派生心率片段，供后来补到的活动/睡眠区间精确重算 |
| 动作证据 | `exercise`；`activity-level` 的 `LIGHTLY_ACTIVE`、`MODERATELY_ACTIVE`、`VERY_ACTIVE` | 代替设备端惯性传感器；与心率和清醒掩码的交集共同构成逐秒资格，至少 30 个合格秒才累计 |
| 睡眠排除 | 已保存的 sleep interval | 常规分钟不在睡眠内累计；明确 exercise 覆盖优先 |
| 静息心率 | `daily-resting-heart-rate` | 仅用于稳定的个人 RHR 基线；当天 RHR 留给恢复指标，避免重复计入 |
| 性别参考 | 已有账户健康资料中的参考性别 | 只用于公开 Banister 公式的性别常数；缺失时不推断、不出分 |
| 最高心率 | 历史非睡眠有效心率分钟的已观测最高 `maxBpm` | 用户明确选择由历史自动获得，不提供手工覆盖；标为估算而非实验室 HRmax |

`time-in-heart-rate-zone` 和 Google 每日心率区间用于展示与交叉校验，不可代替动作证据。心率达到阈值、但 API 没有动作或 exercise 证据的分钟记为“未验证升高心率”，不累加到心肺负荷，也不当作 0。

## 4. 实际全天心肺负荷（`cardio-load-trimp-v3`）

### 4.1 基线与分钟资格

对目标日 `D`：

1. 个人 RHR 基线 `RHR_base(D)` 为 D 之前最近最多 28 个有效日 RHR 的中位数；少于 7 个有效日不计算负荷。7–27 日为“临时基线”，28 日及以上为“稳定基线”。当天 RHR 不进入此基线。
2. `HRmax_est` 是当前已保存的 `google-wearables` source family 中、非睡眠、本地推导覆盖至少 30 秒、`sampleCount >= 1` 且 `100 <= maxBpm <= 230` 的 `maxBpm` 历史最大值；这里不要求动作证据，以避免“先要 HRmax 才能判定动作负荷、又先要动作负荷才能得到 HRmax”的循环。它只是 HRmax 的设备观测代理，不能排除心理压力造成的异常峰值。provenance 必须保存峰值 bpm、分钟 UTC instant、覆盖秒数、样本数和筛选规则版本。若 `HRmax_est <= RHR_base(D)`，该日为 `invalid_hr_reserve`，不计算负荷或使用率，并保存可解释原因，绝不能除以零或把反向心率储备夹成 0。新出现更高的有效观测值时，服务端必须重算全部保留的 v3 日负荷，使同一历史窗口使用同一个观测上限；旧的计算版本保留。该值必须在 UI 中称为“历史观测上限（估算）”，不得写作实验室最大心率。
3. 分钟心率必须有本地推导的心率覆盖。同步时，服务端将原始点在内存中按最多 75 秒 hold 形成按 UTC 分钟裁剪的派生心率片段 `{startOffsetMs, endOffsetMs, bpm}`；它不保存原始点的标识、完整 API 响应或逐点元数据。片段保存是必要的：若活动或睡眠 interval 后到，系统仍能以当时真正重叠的 BPM 重算，而不是拿整分钟平均心率代替。令 `motionMask` 为 active `activity-level` 与 exercise 的并集，`awakeMask` 为非睡眠秒与 exercise 秒的并集，则：

   ```text
   qualifiedSeconds_m = durationSeconds(hrCoverage ∩ motionMask ∩ awakeMask)
   qualifiedBpmSeconds_m = Σ (segment.bpm × segment 与 motionMask、awakeMask 的重叠秒数)
   HR_m = qualifiedBpmSeconds_m / qualifiedSeconds_m
   ```

   上式中的 `hrCoverage` 由派生心率片段的覆盖范围组成，时长按毫秒累计后换算为秒。只有 `qualifiedSeconds_m >= 30` 的分钟才可贡献负荷。这样一分钟内只有 30 秒真正同时具备心率、动作和清醒证据时，最多只累计半分钟，而不会被误算为完整一分钟；`HR_m` 也只代表这 30 秒，而不是整分钟。
4. 令

   ```text
   hrr_m = clamp((HR_m − RHR_base(D)) / (HRmax_est − RHR_base(D)), 0, 1)
   ```

   只有 `hrr_m >= 0.30` 的合格分钟累计负荷。30% HRR 是 Google 在 24/7 Cardio Load 中公开采用的最低阈值，用来排除原始 TRIMP 在全天低心率下的基础累积。

5. 对性别参考为 male，`k = 1.92`；female，`k = 1.67`。每分钟：

   ```text
   baseLoad_m = 0.64 × hrr_m × exp(k × hrr_m)
   load_m = baseLoad_m × qualifiedSeconds_m / 60
   dailyLoad(D) = Σ load_m
   ```

   结果保留一位小数，单位显示为 `TRIMP`。这是公开的、非线性 Banister HRR-TRIMP 形式：心率越高，额外一分钟的负荷越大。不得把它再映射到任意 0–21 分数。

### 4.2 实时、缺口和状态

- 当天一有合格分钟即显示累积负荷；不再要求 120 分钟 `activity-level` 上下文才出分。
- 图表按已观测的有效分钟绘制；未观测和“未验证升高心率”是不同状态，均须显示缺口或说明，不能用连续实线伪装。
- 有高质量全天心率覆盖且没有任何合格活动分钟时，闭合日显示 `0.0 TRIMP`；覆盖不足或动作证据完全未知时显示 `—`，不能把未知写成 0。
- 当前日始终是 `进行中`，同时显示“观测截至 HH:MM”和“有效动作分钟 / 未验证升高心率分钟”。过去日若新同步到数据，24 小时回补会重算该日与受影响周提升基线。
- `activity-level` 稀疏不再阻断已有 exercise 或动作证据分钟的累计；但不会把缺失动作证据的静坐高心率偷算成运动负荷。派生心率片段只保存 75 秒 hold 后、按分钟裁剪的时间范围与 BPM，不保存原始 API 点、标识或响应；任何重算均复用它和已保存的活动/睡眠 interval。

## 5. 本周提升基线

### 5.1 周提升基线，不设固定百分比加量

每日背景活动和正式训练都有显著日波动，不能用日参考取代周参考。每个用户的周从当地周一 00:00 开始。只有一个当地周的 7 个已结束日都满足 `qualifiedDay` 时，它才是 `qualifiedWeek(w)`，且 `weeklyLoad(w)` 才存在并等于这 7 天 `dailyLoad` 之和。任何一天缺戴、低覆盖或未结束时，`weeklyLoad(w)` 是 `undefined`，绝不能把六天或更少的部分和放入 RM4/EWMA4。

首页的当周进度另用 `weekToDateLoad(w)` 表示：它是本周截至当前的已验证日负荷和，只用于展示“已观测进度”；若本周已结束日中有任何非 `qualifiedDay`，它必须标记“本周数据不完整”，不与历史 `weeklyLoad` 混用。

仅当 `w−1` 至 `w−4` 是四个**连续日历** `qualifiedWeek` 时，定义：

```text
RM4(w) = (weeklyLoad(w−1) + weeklyLoad(w−2)
          + weeklyLoad(w−3) + weeklyLoad(w−4)) / 4

EWMA4(w) = 0.4 × weeklyLoad(w−1) + 0.6 × EWMA4(w−1)

weeklyBuildBaseline(w) = max(RM4(w), EWMA4(w))
```

首次获得四个完整周时，`EWMA4` 初始化为该四周的 `RM4`；后续才按递推式更新。`0.4 = 2/(4+1)` 是把 4 个周观察值作为 28 天慢变量的公开 EWMA 取法。`max(RM4, EWMA4)` 与 Google 公开的目标结构一致：RM 使近期持续增加能较快反映，EWMA 使短期中断或单周异常不致让目标剧烈跳变。Google 没有公开其实际 EWMA 常数；0.4 是本产品采用并向用户披露的标准 4 周 EWMA 选择，不声称是 Google 的私有常数。

这不是“每周固定加 10%”：系统综述没有支持 10% 规则是普适、安全的负荷增长率。`weeklyBuildBaseline` 是维持当前适应水平的历史锚点，不是假装有研究支持的预先加量处方。用户选择“循序提高”时，产品把持续超过该锚点的实际周负荷视为 build；下一周的 RM4/EWMA4 自动跟随这份持续完成的高质量负荷。这是**事后、数据驱动的逐周上调**，不是一条在数据不足时也强推的增长率。

示例：四周历史均为 200 TRIMP，某周实际完成 260。下一周 `RM4` 会先升至 215；EWMA 同时向 260 靠近，取较大的一个。若 260 持续，四周窗口和 EWMA 都继续上升，基线自然追上新常态；若仅一次高周又回到 200，基线只会暂时抬升并逐步回落。

### 5.2 校准、数据质量和缺失

| 阶段 | 条件 | 基线行为 |
| --- | --- | --- |
| 不可用 | 少于 7 个连续合格日 | 只显示实际日负荷，不给周提升基线 |
| 临时 | 至少 7 个连续合格日、但不足 4 个 `qualifiedWeek` | 以最近连续 7 日负荷作为临时周锚点；不输出 RM4/EWMA4 分解，标注“校准中” |
| 稳定 | 紧邻当前周之前的 4 个连续日历周均为 `qualifiedWeek` | 使用 RM4 / EWMA4 并按每周一更新 |

`qualifiedDay` 是可复用的质量判定：该日有明确 IANA 时区；有一段以前一夜主睡眠结束至下一夜主睡眠开始定义的清醒窗口；原始心率分钟的本地推导覆盖至少 12 小时、并覆盖该清醒窗口至少 70%；清醒窗口内无超过 4 小时的连续缺口。当前尚未结束的当地日和缺失任一主睡眠锚点的日期都不能进入周基线或可用负荷历史。以上是防止摘表日把训练基线误判为低负荷的数据质量规则，不是人体或医疗阈值。临时阶段，任何低覆盖日都会阻断连续计数；稳定阶段，任何低覆盖日都会使该日所在周不成为 `qualifiedWeek`。缺失周不得跳过后悄悄拼接更早周进入四周窗口：保持上一个成功基线并显示“本周数据不完整”，直到再次形成连续四周；绝不以 0 补入。

首次连接的回填窗口须从既有 35 日提升为至少 **42 个当地日**：7 个前置 RHR 基线日、4 个完整周、睡眠与周一边界缓冲。这样才能在数据质量满足时形成稳定周基线；不足 42 日只可进入临时阶段。

周提升基线一旦已有稳定版本，单周因漏戴或临时同步失败不降低基线；保持上一个成功基线并显示“本周数据不完整”。恢复真实持续降低时，后续高质量周的 RM4/EWMA4 才会自然下调。

### 5.3 “Build” 的动作语义

`weeklyBuildBaseline` 是用户通常已能承受的周负荷锚点，而不是保证安全的硬上限。

- 本周 `weekToDateLoad` 接近提升基线：显示“维持当前节奏”。
- 本周持续超过提升基线、且成为 `qualifiedWeek`：显示“你的新常态正在抬升；下一周会按历史跟随更新”。
- 本周进度低于提升基线且恢复状态较好：可提示“若主观状态也良好，可选择轻到中等强度活动”；不承诺效果、不提供医疗许可。
- 恢复状态较差：不提示用户为了追提升基线补练；但不把既有基线或已发生 TRIMP 扣低。

不得显示 ACWR 的“安全区”、受伤概率、或任何固定危险阈值。

## 6. 今日可用负荷：将恢复放在正确位置

### 6.1 原则

恢复状态不能改写已发生的 TRIMP。它改变的是今天继续增加负荷的可用空间。因此产品必须把“实际负荷”和“可用负荷”分列，禁止将恢复分数乘到 `dailyLoad` 上。

恢复调整没有公开的、可推广的固定百分比公式。为避免伪科学的 `Recovery × 常数`，使用用户自己的历史条件分布，而不是全人群乘数。

### 6.2 个体条件参考公式

1. 使用当天既有的 `whoop-style-v2` `Recovery` 分数，且只接受 `quality` 为 `medium` 或 `high` 的结果。这里的 v2 Recovery 是**持续重算的版本化输入**，不是被冻结的历史常量：其 HRV、RHR、主睡眠、sleep goal、Sleep Performance、前一日 v2 Strain 或各自历史基线发生修订时，Recovery 会按 v2 的既有规则重新计算，进而失效 v3 容量。`provisional`、`unavailable` 与同步过期的恢复数据不调整可用负荷，只显示“恢复校准中”。容量结果必须存储 Recovery 的算法版本、结果 fingerprint 与依赖的 v2 Recovery 日期；本设计不把 v2 的显示分数伪装成经过新验证的医学量表。日后若以独立审阅后的 `recovery-v3` 替代它，容量只能以新版本整体重算，不能混用两种 Recovery 历史。
2. 令 `H(D)` 为 **严格早于 D** 的最近最多 28 个、同时具备 `qualifiedDay`、`dailyLoad` 和 `medium/high` Recovery 的完成日。只有 `|H(D)| = 28` 才进入恢复适配。按 `H(D)` 的 Recovery 分数的个人三分位将历史日分为低、常态、高恢复层；当天按同一人的历史分位归层，不能使用所有用户统一的 33/67 分界。三分位按升序 nearest-rank 定义；若两个边界相同或当天没有可区分的层，恢复适配不可用。
3. 若当天恢复层至少有 7 个同时具备高质量日负荷的历史样本：

   ```text
   capacityByState(D) = percentile_80(
     dailyLoad(i) | i ∈ H(D) 且 i 属于当天恢复层
   )

   globalHighReference(D) = percentile_90(
     dailyLoad(i) | i ∈ H(D)
   )

   usableLoad(D) = min(capacityByState(D), globalHighReference(D))
   utilization(D) = dailyLoad(D) / usableLoad(D)
   ```

4. 同层样本少于 7 个、三分位不可区分或 `globalHighReference <= 0` 时，`usableLoad` 不伪造恢复乘数：前两种情况只在 `globalHighReference > 0` 时退回它并明确标为“恢复适配校准中”；否则 `usableLoad` 与使用率均显示 `—`。不得执行零除。这保证早期数字不会因为任意系数看起来很精确。

`percentile_80` 是“在相似恢复状态下已记录的较高、但非单次最大日负荷”的个人参考；`percentile_90` 抑制单次异常高日。二者是透明的训练规划策略，不是临床容量或伤病阈值。随着用户在各种恢复状态下积累高质量数据，低恢复层通常会形成较低的参考上沿；若其历史行为并不支持这种差异，产品必须诚实显示无明显差异，不能强行扣减一个乘数。

### 6.3 用户界面与行为

首页示例：

```text
全天心肺负荷        42 TRIMP
今日可用负荷        45 TRIMP · 恢复状态已纳入
当前使用率          93%
本周提升基线        210 / 235 TRIMP
```

- 使用率 < 80%：仅事实呈现；若恢复较好且本周进度低于提升基线，可提示可选的低到中等强度活动。
- 80%–100%：提示接近当天个人参考上沿。
- > 100%：提示今天已高于当前恢复状态下的个人历史参考，建议后续降强度；不称为过度训练或医疗风险。
- 恢复数据处于校准中：显示实际负荷、全局日参考和数据限制；不以假的低上限制造警报。

## 7. 持久化、版本与重算

新增版本常量 `cardio-load-trimp-v3`，不能改写 `whoop-style-v2` 记录。`daily_cardio` 的主键为 `(user_id, civil_date)` 且版本约束为 v2，`metric_results` 的名称/版本约束也只允许 v2；它们不能承载新结果。迁移必须保留这两张 v2 表并新增下列 v3 专用表：

| 实体 | 关键字段 |
| --- | --- |
| `heart_rate_minute_evidence` | 与分钟聚合相同的 user/source/minute 唯一键、75 秒 hold 后按分钟裁剪的 `{startOffsetMs, endOffsetMs, bpm}` 派生片段；不保存 API 原始点标识、原始响应或逐点元数据 |
| `daily_cardio_loads` | `(user_id, civil_date, metric_version)` 主键、TRIMP、合格/未验证分钟及秒数、RHR 基线、观测 HRmax、动作来源、覆盖与质量、input fingerprint |
| `weekly_cardio_baselines` | `(user_id, week_start_civil_date, metric_version)` 主键、RM4、EWMA4、`weeklyBuildBaseline`、校准状态、输入周 fingerprint |
| `daily_load_capacities` | `(user_id, civil_date, metric_version)` 主键、实际负荷、可用负荷、使用率、恢复层、样本数、是否回退全局参考、质量、Recovery 版本/日期/fingerprint |

旧首页/历史接口继续从 v2 表读取，直至 v3 API 和 UI 同时切换；切换后仍允许按版本读取旧记录，不做 in-place 覆盖。删除用户或断开连接时，现有健康数据清理事务必须将上述四张 v3 表一并删除。派生心率片段仍是敏感健康数据，适用与现有心率聚合相同的访问控制与删除路径。

因为 `RHR_base(D)` 与 `H(D)` 都按“最近 28 个有效记录”而非固定 28 个日历日取样，缺戴时影响可跨越超过 28 个日历日；因此任何影响分钟心率、activity level、exercise、睡眠、RHR、HRV、sleep goal、Sleep Performance、v2 Recovery、参考性别或时区的变更，都必须从最早受影响日重算至当前保留窗口末尾，而不是以“+28 日”截断。流程为：先重算受影响的 v3 日负荷；再重算其后的 v2 Recovery 输入链与 v3 容量；最后从最早受影响周起重算全部后续周提升基线直至当前周。参考性别或历史观测 HRmax 变化时，须重算全部保留的 v3 日负荷、容量和后续周提升基线。同步仍使用既有心率/活动 24 小时回补窗口；每小时更新当前日和最近窗口，不得在页面渲染时调用 Google API。

历史回填完成时批量计算最近 42 日；若新 HRmax 估计出现，使用单一版本化任务重算受影响历史，避免页面在同一批数据中混合不同 HRmax 估计。

## 8. API 与 AI Coach 契约

Dashboard API 只返回经服务端验证的日负荷、可用负荷、周提升基线、当周已观测进度、数据质量、观测截至时间、简短输入摘要与版本。不得返回派生心率片段、OAuth 令牌、完整 Health API 响应或未验证高心率的精确时间线。

AI Coach 只可引用：实际 TRIMP、可用负荷使用率、提升基线进度、恢复质量与覆盖状态。它不得声称用户“安全”“危险”“过度训练”或输出确定性的医疗/受伤判断。恢复差时的允许输出是“不要为了追提升基线而加练、结合主观感受调整”；而不是禁止性医疗指令。

## 9. 验收与测试

实施必须先补充失败测试，再写实现。至少覆盖：

1. 分钟 HRR-TRIMP：30% 阈值、男女 `k`、非线性增长、RHR/HRmax 边界、四舍五入；低于阈值为零；`HRmax_est <= RHR_base`（相等和更低）为 `invalid_hr_reserve`，不发生除零或反向夹取。
2. 动作证据：exercise 或 active level 计入；睡眠和未知动作心率不计入；稀疏 `activity-level` 不再触发旧的 120 分钟硬门槛。
3. 历史 HRmax：新高值导致 v3 重算、旧 v2 不变、无参考性别/RHR/HRmax 时不出分且原因可见。
4. 当前日：有效贡献一出现即有进行中负荷；观测缺口和未验证升高心率不被画成连续数据；不完整不等于 0。
5. 逐秒资格：仅有 30 秒 HR/动作/清醒交集时只累加半分钟负荷，且 HR 只取该交集内的派生片段；交集不足 30 秒不累计；75 秒 hold 不会越过一分钟或睡眠/动作边界；活动/睡眠 interval 迟到后仍能用派生片段精确重算。
6. 周基线：仅 7 个 `qualifiedDay` 的周可生成 `weeklyLoad`；部分周只显示 `weekToDateLoad`、绝不进入 RM4/EWMA4；覆盖 RM4、EWMA4、`max` 选择、一次高周、持续高周、低周、漏戴周冻结、周一时区边界、7/28 天校准状态；文案不把基线称作固定加量处方。
7. 可用负荷：实际 TRIMP 不会因 Recovery 改写；同恢复层样本足够时使用条件 P80；不足时仅回退全局 P90 并标校准；v2 Recovery 的 HRV/RHR/睡眠/sleep goal/Sleep Performance/前日 v2 Strain 或其历史基线变化都会确定性地重算后续 v3 容量，使用率和超过参考上沿的文案正确。
8. 迁移与可追溯性：新 v3 表可与 v2 并存；迁移不触碰 v2 行；输入 fingerprint 或观测 HRmax 变化会按规定范围重算日/周/容量；同一版本、同一输入的结果稳定；数据来自同一 `google-wearables` source family。

## 10. 明确不做

- 不声称 API 结果等同 Google App 的私有 Cardio Load；设备端惯性传感器不可通过当前 API 获得。
- 不做 WHOOP 0–21 的仿制映射，不使用旧 `0.5/1/2/3` 权重与指数饱和展示函数。
- 不以 ACWR、Recovery 或可用负荷给出医疗安全阈值、受伤概率或诊断。
- 不通过固定 10% 周增量、固定 Recovery 乘数、或用户手填 HRmax 来制造确定性。
