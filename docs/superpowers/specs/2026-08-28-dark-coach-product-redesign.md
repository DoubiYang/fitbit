# 深色健康教练全站视觉重设计

**状态：** 用户已确认，待实现
**日期：** 2026-08-28
**视觉方向：** 本任务中用户选择的第二张移动端概念图（深墨底、萤绿/青绿状态色、照片主导的健康教练界面）。

## 1. 目标与范围

为「节律」的全部用户可见网页统一成一套手机优先的深色健康教练体验。目标不是改变健康计算、OAuth、照片处理或 Google 同步机制，而是让用户在手机上更快看懂当前状态、明确下一步动作，并在餐食工作流里拥有足够的信任感。

本次覆盖现有页面和它们的空态/受限态：

| 页面/组件 | 路径或位置 | 目标 |
| --- | --- | --- |
| 今日仪表盘 | `/rhythm` | 先展示今天的恢复与行动建议，再呈现解释性指标和餐食入口。 |
| 餐食新建 | `/rhythm/meals/new` | 用整屏照片入口代替默认文件表单，让同意与开始识别成为清晰的两步。 |
| 餐食审阅/已保存 | `/rhythm/meals/[id]` | 让菜品、完整营养、AI 建议、保存与显式同步呈连续的审阅工作流。 |
| 账户 | `/rhythm/account` | 用连接状态和下一步操作替代说明文字墙。 |
| 隐私与条款 | `/rhythm/privacy`、`/rhythm/terms` | 统一为容易阅读的深色信息页，并校正与当前已实现行为不符的技术事实披露。 |
| 全局空态、错误与导航 | 所有上述页面 | 让受限状态可理解、可操作，且保持既有原因文案。 |

API 路由、OAuth callback、内部 worker 路由及现有业务规则不在视觉重构范围内。不会新增产品页面或改变数据模型。

## 2. 现状审阅依据

2026-08-28 在 390 × 844 视口实际截取并检查了仪表盘、账户、隐私和餐食新建页面。所有页面没有横向溢出，但存在共同问题：主体内容过小且停在左上角；大面积背景没有承担信息层级；默认输入控件和同等权重的白卡使「开始识别」与「保存/同步」缺少优先级；账户与法务信息没有清晰的状态和阅读节奏。

视觉参考只提取原则，不复制品牌界面：

- Google Health：轻量的健康数据分组、短状态标签、明确的当前行动。
- WHOOP：深色背景上的强状态层级、单一高亮行动色、把日常决策放在指标前面。

## 3. 设计语言

### 3.1 色彩与表面

- 页面底色使用近黑蓝 `#0B1117`，内容层从 `#111B24` 到 `#172431`，不使用纯黑。
- 正文为柔和近白，二级文字为蓝灰；分隔仅用低对比 hairline，避免每一项都包一张卡。
- 萤绿是「准备就绪、可执行、成功」的唯一强调色；青绿表示进行中；琥珀表示需要注意；红色仅用于错误。
- 同一屏只允许一个萤绿主要 CTA。状态色不用于装饰性大面积背景。

### 3.2 排版与密度

- 使用系统中文无衬线字体；数字启用 tabular figures。
- 页面标题 32–40 px、区块标题 20–24 px、正文 15–16 px、说明最小 13 px。避免现状中过小的密集说明字。
- 手机左右边距 20 px，主要区块之间 24–32 px；行项目用 16 px 内边距和分隔线组织。
- 圆角用于可操作的容器（12–20 px）；不再出现大量漂浮白卡或厚阴影。

### 3.3 图标与视觉资产

- 使用一个现有、开源、线性但圆润的图标库；不使用 emoji、手写 SVG、文字充当图标或 CSS 画图。
- 餐食流程允许照片预览时，照片是主视觉；未选择照片时以真实图标和清晰的上传标签表达入口，不以默认原生文件控件作为可见 UI。
- 已保存餐食不显示照片占位，也不持久化或重新展示图片，继续遵守现有隐私边界。

## 4. 全局壳层与导航

手机端的主页面（今日、账户、隐私、条款）采用 64 px 高、加上 `safe-area-inset-bottom` 的持续底部导航：`今日`、`餐食`、`账户` 分别链接到现有 `/rhythm`、`/rhythm/meals/new` 和 `/rhythm/account`；当前位置有文字与图标的双重选中状态。隐私和条款将“账户”保持为当前导航项。它不创建新路由。

餐食新建、草稿、已保存和恢复页面是聚焦工作流：隐藏全局底部导航，只保留顶部返回入口和一个 56 px 高、加上安全区的餐食固定操作栏。该操作栏的 `z-index` 高于滚动内容但低于 dialog，主内容末尾预留其完整高度；两类固定栏绝不同时出现。768 px 以上改为有限宽度的阅读/工作区：仪表盘、账户、法务内容居中；餐食审阅可使用主内容和 AI 侧栏两列，但不改变动作顺序。

## 5. 屏幕行为

### 5.1 今日仪表盘

首屏依次呈现：当天日期与同步新鲜度、小而明确的恢复状态、今天的一句建议，以及「记录餐食」主操作。恢复/睡眠/训练三项改为有节奏的纵向指标模块：分数、数据质量和一句解释在同一行或相邻层级，避免三张内容相同的大白卡。

空数据或校准中时不伪造分数；使用当前已有的说明和证据，配合「连接账户」或「记录餐食」等真实下一步。

### 5.2 餐食新建

首屏是照片优先的“准备分析”区：用户先选择/拍摄照片；照片未选时显示大型可点按上传面，选中时显示本地预览和替换入口。餐次使用明确的分段选择；时间是一行原生可访问字段；同意用现有 checkbox 语义但按设计语言呈现。未选择照片或未同意时，开始识别按钮禁用并说明缺失前提。

页面只在用户同意后把当前照片送入已有的视觉识别请求；该请求继续由服务端的模型凭证认证，照片不落盘。OAuth token、session token 和刷新 token 不得进入视觉模型或餐食助手请求；餐食助手只接收当前结构化餐食和本次问题。

### 5.3 餐食审阅与同步

审阅页顶端显示餐次、进食时间和同步状态。菜品、营养组、AI 建议按单一纵向工作流排布：

1. 菜品与食材行有明确的“编辑”入口；修改食材仍只重算目标菜。
2. 能量与宏量默认展开，维生素、矿物质和其他成分可折叠；每行可直接打开单项编辑。
3. AI 区以“待处理建议”表达，不自动应用；当前页面会话可继续，刷新后不恢复。
4. 固定底部动作继续区分“保存修改”和“同步这一餐”。草稿只显示保存；保存后只有服务端允许同步时才高亮同步。同步、恢复和权限不足状态沿用现有禁用规则与原因。

同步安全状态是视觉不可变约束：`syncing` 和 `recovery` 一律锁定编辑；存在任一 `unknown` point 时，页面仅显示“检查同步状态”这个恢复动作，它只触发现有 generation 对原 point name 的精确 GET，绝不创建新 name、重新排队或显示可再次 POST create/delete 的操作。所有 `unknown` 消除后，若仍有 `failed_action_required`，才显示既有的重新授权/开启写回原因，并由现有状态机恢复原来的已知 pending operation。视觉层不得把 recovery 伪装成普通“再同步一次”。

照片预览只在当前的草稿客户端状态中出现；保存后进入已保存 URL 时，仍不恢复预览、聊天或建议。

### 5.4 账户、隐私与条款

账户页以单个连接状态模块开场：现有 `unconfigured`、未连接、可用、授权失效和重新授权状态各有短说明与一个明确操作。密钥配置等开发者说明仅在现有 `unconfigured` 状态展示，使用等宽小片段和复制友好的样式，不引入“本地/部署环境”判别或新的数据契约。

隐私与条款使用深色阅读面、清晰标题、较宽行距和一个固定的返回/账户入口。隐私页必须把已过期的“本阶段不会拉取、展示或向模型发送真实健康记录”替换为准确的事实说明：同步的健康快照会被本地读取和展示；用户同意后当前餐食照片仅用于一次视觉识别；餐食助手仅收到结构化餐食和问题；OAuth 凭证加密保存在服务端且不进入模型。实现前将最终隐私文案交给产品负责人确认；条款的法律含义不扩展。

## 6. 可访问性与交互约束

- 所有主要触达目标至少 44 × 44 px；焦点可见，键盘顺序与视觉顺序一致。
- 颜色从不作为唯一状态说明：同步、数据质量、错误和选中态均有文字或图标标签。
- 继续使用语义 button、label、input、dialog、aria-expanded 和已有 modal 焦点管理；设计不能把 checkbox 或文件输入的可访问名称移除。
- 支持 `prefers-reduced-motion`；只允许短、非必要的透明度/位移动画，不能以动画表达完成或错误。
- 深色对比度达到正文可读标准；照片上的文字必须有实色或足够的遮罩承托。

## 7. 验收标准

- 在 320、390、768 px 下，所有用户可见页面无横向溢出；主页面只出现全局底部导航，餐食工作流只出现餐食操作栏，内容末尾永不被固定栏遮挡。
- 从仪表盘进入餐食新建、选择照片、同意、识别、编辑、保存、显式同步的原有链路仍可操作；没有视觉改动造成提前 Google 写入。
- 已保存餐食、AI 请求和视觉层均不新增照片、AI 消息、建议、token 或营养历史的持久化。
- 同步恢复在任一 `unknown` 存在时只执行精确 GET；页面没有会造成第二次 Google create/delete POST 的视觉入口或 CTA。
- 深色状态色、文字、图标和按钮共同表达可用/禁用/错误，键盘焦点可见。
- `pnpm test`、`pnpm lint`、`pnpm build` 通过；对全局 shell、仪表盘、账户与餐食编辑器增加或更新结构/可访问性测试；在相同 390 px 视口将实现截图与已选视觉目标并列设计 QA。
