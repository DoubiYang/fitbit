# Google Health API 接入与验证设计

**状态：** 草案，待用户审阅
**日期：** 2026-08-23
**对应工作项：** 2. 验证 Google Health API 的授权、拉数、写回和多用户审批

## 1. 目标

在开始产品开发前，证明系统可以在多用户场景下安全地：

1. 让用户用 Google/Fitbit 账号完成授权；
2. 拉取一期所需的原始健康和活动数据；
3. 读取及修改由本产品创建的餐食记录；
4. 知道哪些数据因权限、地区、设备或 API 限制而不可用。

本期主通道是 **Google Health APIs（原 Fitbit Web API）**。Health Connect 是 Android 本机数据层，不作为一期核心依赖；仅在后续需要接入非 Fitbit 设备时评估。

## 2. 已知边界

| 项目 | 设计结论 |
| --- | --- |
| Google 私有分数 | 公开 API 不提供 Readiness、Sleep Score、Cardio Load 或 Target Load；本产品只使用原始数据。 |
| 多用户分钟级数据 | 心率等 intraday 数据可能需要单独的数据访问审批；在审批前不能把它列为上线前提。 |
| Health Connect | 是 Android 设备侧 SDK；无法替代服务端的多用户 OAuth 数据管道。 |
| 营养写回 | Web API 支持食物日志的创建、修改和删除；仅写回用户确认后的记录。 |
| 地区能力 | Google Health Coach 的地区限制不应影响本产品的数据管道，但实际 OAuth、设备数据和 API 可用性必须用测试账号验证。 |

## 3. 目标架构

```text
用户浏览器
  └─ OAuth 授权 ─→ 产品后端 ─→ Google Health API
                         │
                         ├─ 加密保存 refresh token
                         ├─ 原始数据与来源记录
                         ├─ 标准化日数据 / 自建指标
                         └─ 已确认餐食写回
```

访问令牌与 refresh token 只保存于后端，不进入浏览器、前端日志或 AI 上下文。每个用户的 API 凭证、原始记录、派生数据和删除任务必须按用户 ID 严格隔离。

## 4. 一期数据清单

### 必需数据

| 域 | 用途 | 最低可接受粒度 |
| --- | --- | --- |
| 睡眠日志与阶段 | 睡眠完整度、规律性、睡眠债 | 每次睡眠会话和阶段汇总 |
| HRV、静息心率 | 恢复信号的个人基线和偏离 | 每日值 |
| 心率与训练/活动 | 训练负荷、训练会话解释 | 会话汇总；获得批准后可用分钟级数据增强 |
| 步数、距离、热量 | 日常活动上下文 | 每日汇总 |
| 呼吸率、SpO₂、皮温 | 仅作趋势补充与异常说明 | 每日/夜间汇总，缺失可降级 |
| 食物日志 | 避免重复、支持写回和营养上下文 | 餐食条目 |

### 数据来源规则

- 保存每条数据的外部记录 ID、来源、开始/结束时间、抓取时间和原始负载哈希。
- 同一餐食写回时使用本产品的外部 ID 做幂等关联；更新与删除只操作本产品创建的记录。
- 外部来源间存在冲突时，保留原始记录，不覆盖设备数据；在标准化层按预先定义的来源优先级选择展示值。

## 5. 同步生命周期

1. **授权：** 显示最小权限清单和用途，用户明确同意后进入 OAuth。
2. **首次导入：** 尝试导入最近 90 天，用于 28 天基线和趋势；无数据或无权限时如实显示可用范围。
3. **增量同步：** 以订阅通知为优先；在验证期使用可追踪的日轮询作为兜底。
4. **标准化：** 校验时间区、重复、异常值和来源，写入不可变原始层及可更新的日汇总层。
5. **断开与删除：** 撤销 token、停止任务、删除令牌与用户选择删除的原始/派生数据，并记录完成状态。

## 6. 营养写回规则

只有满足以下条件才写回：

- 用户已确认餐食名称、时间、份量和估算营养；
- 系统已检查本产品外部 ID 是否已成功写入；
- 写回接口返回成功并持久化外部日志 ID。

用户编辑或删除时，优先更新/删除同一外部 ID。若外部操作失败，界面清楚显示“本产品已保存，Google Health 未同步”的可重试状态，绝不假装成功。

### 幂等性与不确定响应恢复

提交前先创建不可变的本地 `food_write_operation`，其字段至少包括：`operation_id`、`user_id`、`local_food_entry_id`、规范化请求负载哈希、状态、请求时间、尝试次数和 `provider_food_log_id`。`local_food_entry_id` 在该表中唯一，状态机为：

`prepared → in_flight → confirmed | unknown | failed`

- API 正常返回时，从响应持久化 `provider_food_log_id`，状态变为 `confirmed`；后续编辑、删除只能使用该映射。
- 超时、连接中断或响应无法解析时，状态变为 `unknown`，**禁止自动再次 POST 创建**。先查询该用户同一时间窗口内、具有完全相同规范化营养负载的日志：仅发现一个候选时人工或规则确认映射；零个或多个候选时保留 `unknown` 并提示用户，不重发创建请求。
- 只有验证阶段确认提供方支持稳定的客户端关联字段或幂等键后，才允许安全自动重试；否则一期宁可出现“待确认同步”，也不以重复餐食换取表面成功率。
- 同一用户的手动 Google Health 餐食与本产品来源不自动合并或删除；界面只标示潜在重复来源。

## 7. 验证计划与退出条件

### 验证顺序

1. 注册应用并完成个人开发者账号授权；
2. 验证各 scope、refresh token、首次 90 天导入与日增量同步；
3. 验证睡眠、HRV、RHR、训练、食物日志的实际字段和数据质量；
4. 创建、编辑、删除一条测试餐食，检查 Google Health 侧的可见性与重复行为；
5. 提交或确认多用户 intraday 数据访问审批要求；
6. 以两到三位不同设备/地区的同意测试用户重复验证。

### 通过标准

- 授权、刷新与撤销均可完整跑通；
- 最小数据集可稳定获得，且每项可用性被记录；
- 一条已确认餐食可被准确创建、编辑、删除且不重复；
- 对网络超时的写入会进入 `unknown` 并可恢复或提示人工处理，不产生盲目重试；
- 不依赖未获批的分钟级数据也能生成一期指标；
- 风险、限制和必要审批有书面记录。

## 8. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 多用户 intraday 未获批 | 先用会话和日汇总计算负荷；将高频 HR 作为增强能力。 |
| 设备未同步或字段缺失 | 显示数据新鲜度，降低指标置信度，不生成强结论。 |
| 第三方与本产品重复写餐食 | 只选一条写回路径、写入外部 ID，并提供来源/删除说明。 |
| API 规格变化 | 以 provider adapter 封装 API，保留原始响应并增加契约测试。 |
| 用户撤回同意 | 立即阻断同步与 AI 数据检索，完成可审计的删除流程。 |
