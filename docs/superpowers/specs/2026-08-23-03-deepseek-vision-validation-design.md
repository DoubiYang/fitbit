# DeepSeek Vision 餐食识别验证设计

**状态：** 草案，待用户审阅
**日期：** 2026-08-23
**对应工作项：** 3. 验证 DeepSeek Vision 的中餐识别效果、成本与稳定性
**运行时以哪份为准：** 照片不落盘、一餐一张图、Vision JSON、营养计算时机与 Google 写回，以 [2026-08-26-photo-nutrition-google-health-design.md](2026-08-26-photo-nutrition-google-health-design.md) 为准。本文第 3.7 节的 24 小时 / 30 天存图和第 4 节 `meal_candidates` 示例已被取代。评测集、holdout 门槛、成本与隐私审阅仍然有效。

## 1. 目标

验证 `deepseek-v4-flash-vision-exp` 能否作为一期“拍照记餐”的视觉候选模型。它的职责是从餐食照片中提取可供用户确认的候选信息，不承担医疗判断，也不是营养数据库的唯一真相来源。

一期不锁定单一厂商。系统必须通过模型网关调用视觉模型，以便评测不达标、价格变化或可用性异常时切换供应商。

## 2. 模型职责划分

| 任务 | 一期默认方案 | 原因 |
| --- | --- | --- |
| 餐食图片理解 | `deepseek-v4-flash-vision-exp` | 官方支持图片与 OpenAI 兼容接口；该候选模型的 JSON／工具调用契约须在本验证中实测。 |
| 日常中文教练 | `deepseek-v4-flash` | 普通文本对话不必调用实验性视觉模型。 |
| 热量/宏量计算 | 已获授权的中餐营养数据库 + 版本化菜谱/份量换算 | 视觉模型只能给候选和范围，不能作为精确营养事实。 |
| 写回 Google Health | 后端受控工具 | 模型不能直接拥有外部写入凭证。 |

## 3. 用户流程

1. 用户在移动端打开相机或上传照片；首次使用前单独同意“将本张图片发送给 DeepSeek 识别”。拒绝时直接进入手动搜索/快速填写。
2. 客户端压缩图片、移除 EXIF、检测人脸/证件等明显敏感背景并提示裁剪；服务端生成短时请求负载。
3. Vision 模型返回结构化候选：菜品、食材、份量范围、可见/不可见部分、置信度和需确认项。
4. 营养服务按候选匹配版本化营养数据库与菜谱规则，得到可解释的**估算范围**；无法匹配、范围过宽或共享份量未确认时不展示热量。
5. 用户逐项确认或修改菜品、份量、餐次和时间。
6. 用户点击保存后，记录写入本产品；如开启写回，再创建 Google Health `nutrition-log`。后续编辑匿名餐食时删除旧 log 后创建新 log，不尝试 PATCH。
7. 原图在模型成功返回或请求失败后 24 小时内删除；用户选择“保留用于重新识别”时最长保存 30 天。保留经确认的结构化餐食、数据库版本和计算依据，不保留 base64 请求体。

## 4. 结构化输出契约

模型输出必须为 JSON，且不得省略不确定性。服务端以 JSON Schema 验证字段、数值范围和枚举值；模型的 `confidence` 只决定确认页的提示强度，不直接决定热量、写回或健康建议：

```json
{
  "meal_candidates": [
    {
      "name_zh": "番茄炒蛋",
      "ingredients": ["鸡蛋", "番茄", "食用油"],
      "portion_g_range": {"min": 140, "max": 220},
      "visible_fraction": "partial",
      "confidence": 0.72,
      "needs_confirmation": ["油量", "实际食用比例"]
    }
  ],
  "photo_quality": "usable",
  "global_uncertainties": ["存在共享菜，无法判断用户实际摄入量"]
}
```

禁止模型直接返回“精确摄入 723 kcal”这类不可解释结论。营养服务可以给出估算区间，确认页必须允许用户调整。

## 5. 营养计算与写回边界

一期先选定一个具备商业使用许可的中国食物营养数据源，并维护“菜品/食材别名 → 食物或版本化菜谱”的映射。每次估算保存 `nutrition_database_version`、`recipe_version`、份量换算、可见比例和区间来源；用户可在确认页查看这些依据。

模型只提出候选菜品、食材和份量范围。营养服务以用户确认的份量计算能量、蛋白质、碳水和脂肪范围；油量、共享比例、主食配菜或包装规格未知时必须追问。找不到合适映射、最终能量区间宽度超过中点的 100%，或共享比例未确认时，不预填 kcal，只保留可编辑候选。

Google Health 的 Food 数据库不可由本产品创建或修改，因此一期将照片餐食作为匿名 `nutrition-log` 写入。匿名 log 不可更新：本产品每次编辑形成新的餐食版本，Google Health 侧删除旧版本后创建新版本；写回失败状态遵循 API 验证文档。

## 6. 隐私与安全设计

- API key 只在服务端保存；浏览器不直连模型供应商。
- 不使用公开图片 URL，优先以短时 base64 请求发送；这只避免公网 URL，不改变“图片会被传给 DeepSeek”的事实，必须在拍照前明示接收方、用途、保存期限和撤回方式。
- 上传前移除 EXIF 定位信息，限制格式、尺寸与恶意文件；请求中不附带用户名、Google Health 原始记录、精确位置或可识别用户的 `user_id`。
- 默认不将照片作为长期用户档案；删除策略见第 3 节。日志只保留最小的响应哈希、模型/提示词/营养数据库版本和用户修正，不记录图片、base64 或模型隐藏推理过程。
- 上线前对 DeepSeek 及任何备用模型完成数据流、地域、保存、人工访问、删除与事件通知的供应商审阅；不满足要求的供应商不得接收图片。

## 7. 评测集与方法

### 评测集

建立至少 80 张、经本人同意的真实餐食照片；每张在定稿提示词和模型版本冻结前不得用于调参，另保留至少 20 张完全不参与调参或阈值制定的 holdout 图：

- 单一中餐菜品、盖饭/粉面、火锅/共享菜、早餐、零食和包装食品；每类至少 10 张，可多标签但不以同一张补足两个类别配额；
- 光线不足、俯拍、复杂背景、部分遮挡等真实情形；
- 每张由两位标注者独立准备参考菜品、可见食材、称重份量、菜谱/包装营养依据和可接受营养范围；分歧须记录并在评测前裁决。

不使用含个人面部、证件、住址或其他敏感背景的图像。

### 衡量指标

| 指标 | 说明 |
| --- | --- |
| 菜品候选可接受率 | 用户认可候选或仅轻微修改名称的比例。 |
| 份量修正率 | 用户需要显著调整模型份量区间的比例。 |
| 营养估算误差 | 与称重和菜谱/包装参考范围的偏差；以能量范围覆盖率、区间宽度和中点相对误差评价。 |
| 不确定性召回 | 遇到共享菜、油量、遮挡等情况时，模型是否主动提示需确认。 |
| 延迟与失败率 | 拍照到可编辑结果的 p50/p95，以及请求失败、格式失败比例。 |
| 单餐成本 | 图片 token、文本输入和结构化输出合计成本。 |

## 8. 通过标准

模型通过一期候选资格的最低条件：

| 门槛 | 通过标准 |
| --- | --- |
| 菜品候选可接受率 | 至少 80% 的照片中，用户接受 top-3 中的菜品候选，或只作轻微名称修正。 |
| 份量大幅修正率 | 不高于 60%；“大幅”指用户确认份量落在模型区间外，且偏差超过区间中点的 30%。 |
| 能量估算 | 对单人份且完成份量确认的 holdout 图片，人工参考 kcal 落在最终估算区间内的比例至少 80%，区间中点的中位相对误差不高于 25%。共享菜、火锅或未确认食用比例不得计入该指标，且不得自动展示 kcal。 |
| 宏量估算 | 对同一 holdout 集，蛋白质、碳水、脂肪三项中至少两项的参考值落在最终区间内的图片比例至少 70%；无法达到时只保留菜品候选和手动编辑。 |
| 不确定性召回 | 对人工标注为共享菜、遮挡或油量不可见的样本，至少 90% 明确列出相应需确认项。 |
| JSON 有效率 | 首次响应或一次受控重试后，至少 99% 通过 schema 校验。 |
| 请求稳定性 | 模型/网络不可恢复失败率低于 2%，p95 从用户确认照片到结果可编辑不超过 8 秒，包含压缩、上传、模型调用和一次受控重试。 |
| 成本 | 单张餐食图的模型成本（图片、提示词、最多 500 输出 token、一次受控重试及失败请求摊销）不超过人民币 0.02 元；按供应商响应 `usage` 和评测当天价目表记录。 |
| 安全 | 零条高严重度违规：不得自动保存/写回，不得输出医疗诊断或把低置信估算伪装成精确事实。 |

任意强制门槛不通过时，模型不能作为一期默认视觉提供商；可以修订提示词、确认流程或更换 `VisionProvider` 后重新完整评测。阈值只在用户书面批准后才能修改。

## 9. 降级与替换策略

- 图片质量差、模型超时或结构校验失败：回退为手动搜索/快速填写，而不是阻塞记录。
- 模型低置信度：只显示候选，不预填热量。
- 供应商不可用或评测不达标：通过 `VisionProvider` 接口切换模型；前端和营养确认流程不变。
- 任何模型输出都必须经过 JSON schema 校验和业务规则校验。

## 10. 研究依据

DeepSeek 官方文档确认 `deepseek-v4-flash-vision-exp` 支持图片与 OpenAI 兼容 Chat Completions/Responses API；图片会按尺寸 token 化，单张最多 384 image tokens，并受请求体和图片尺寸限制。JSON 输出仍需提示词、Schema 与业务校验共同保证，且可能出现空内容或截断。模型名称含 `Exp`，因此本设计将它视为候选而非不可替换依赖。

Google Health API v4 的 Nutrition 文档确认：Food 数据库为只读；匿名 `nutrition-log` 可创建但不可更新，修正时需要删除后重建。
